# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

BilibiliSpeed is a fork of Bilibili NEXT (https://github.com/wzk112/Bilibili-NEXT), an unofficial Bilibili client for macOS 26+ (SwiftUI, Liquid Glass, AVPlayer) with an iOS / iPadOS 26+ development preview. User-facing docs (README, CHANGELOG, QA, IOS_STATUS) are written in Chinese; keep that convention when editing them.

## Commands

Requires macOS 26+, Xcode 26+ (Xcode 27+ for iOS), Swift 6.2+.

```sh
swift test                                          # app tests (Tests/BiliGlassTests, swift-testing)
swift test --filter CDNSelectionTests               # single suite / test
swift test --package-path Vendor/BiliKitCore        # vendored playback/networking library tests
Scripts/build-app.sh                                # release build + signed .app (default: ../BilibiliSpeed.app; override APP_DIR)
Scripts/build-ios.sh                                # unsigned iOS simulator build
IOS_PLATFORM=device DEVELOPMENT_TEAM=TEAM IOS_DEVICE_ID=UDID Scripts/build-ios.sh
python3 Scripts/generate-ios-project.py             # regenerate Apps/iOS/BilibiliSpeed.xcodeproj
python3 -m unittest Scripts/tests/test_validate_ipa.py  # IPA packaging validation tests
Scripts/package-release.sh                          # release artifacts; requires a clean committed tree
```

Opt-in env flags for tests: `BILIGLASS_LIVE_TEST=1 BILIGLASS_DOWNLOAD_TEST=1` (network integration: public data, QR code, test download, offline playback — never posts comments/danmaku), `BILIGLASS_BVID`, and `BILIGLASS_BAS_FIXTURE=/abs/path/danmaku.json` (real BAS data; not distributed).

Signing: `build-app.sh` picks the first local "Apple Development" identity (or `SIGNING_IDENTITY`), falling back to ad-hoc. Don't alternate identities between builds — it re-triggers Keychain authorization.

## Fork-specific

- The only feature difference from upstream is the offline speed list (`Playback.offlineSpeedOptions` in `Sources/BiliGlass/Player.swift`); see `BILIBILISPEED_SPEC.md`.
- Bundle IDs, the Keychain service (`Vault.sessionService`), Application Support/Caches folder names and the iOS URL scheme are renamed so the app can coexist with Bilibili NEXT. Keep them distinct from upstream when merging upstream changes.
- Swift module/target names (`BiliGlass`, `BiliKitCore`) and the macOS executable name are intentionally unchanged to keep upstream merges small.
- `QA.md`, `IOS_STATUS.md`, `RELEASE_NOTES.md`, `CODE_REVIEW.md` are upstream records and were not re-verified for this fork.

## Architecture

- `Package.swift` builds one executable target `BiliGlass` (macOS app, Swift 5 language mode) from a flat `Sources/BiliGlass/` directory. It depends on the local package `Vendor/BiliKitCore` (products `BiliModels`, `BiliNetworking`, `BiliPlayback`; internal `BiliApplication` holds use cases like playback timeline and watch-progress sessions).
- `BiliKitCore` is a vendored, modified MIT component (from BiliKit-Mac). Playback works by converting Bilibili DASH streams into HLS served from a local loopback server (`BiliPlayback/Bridge`: `DASHToHLSBridge`, `HLSPlaylistBuilder`, `LoopbackPlaybackServer`) using HTTP Range clients (`BiliNetworking/Range`) and SIDX parsing. Modifications to vendored code must be recorded in `THIRD_PARTY.md`.
- App-level playback layers on top of this: `CDNSelection` (multi-CDN probing, failover with media-identity checks), `ParallelVideoStream` (concurrent ≤1 MiB chunk reads delivered in order, adaptive concurrency), `PlaybackDiskCache` (read-ahead to `~/Library/Caches/BilibiliSpeed/Playback`, cleaned by `PlaybackTemporaryFiles` at launch/terminate), `Player.swift` (session + `NativePlayer` NSViewRepresentable).
- `Store.swift` is the central `@Observable` app state (navigation `Destination`, playback, guide, fullscreen), created in `BiliGlassApp.swift` and passed down to views. `API.swift` holds core models and the Bilibili API client; `Vault` stores login in the Keychain.
- Danmaku is natively rendered: `Danmaku*.swift` (normal modes), `SpecialDanmaku.swift` (mode 7), `BAS.swift` + `SVGPath.swift` (mode 9, interpreted — no JS execution). Mode 8 is unsupported.
- WebKit is used only for official captcha verification (`OfficialChallenge`, `WebPanel`).

### iOS app shares macOS sources

`Apps/iOS` has its own `Mobile*.swift` UI but compiles a hand-picked subset of `Sources/BiliGlass/*.swift` listed in the `SHARED` array of `Scripts/generate-ios-project.py`. The `.xcodeproj` is generated by that script and checked in — edit the script (not the project) when adding/removing files, then regenerate. Shared files must compile on both platforms (`#if os(...)` guards). UI tests: `Apps/iOS/UITests/MobileSmokeTests.swift` via the `BilibiliSpeed` scheme.

## Conventions

- Playback changes should be verified with an actually rendered video, not just parser success or AVPlayer ready status; cover quality switching, seek, fullscreen, pause/resume, download completion and temp-file cleanup when touched.
- Interaction writes (coin, triple-like, comments, messages) must not auto-retry; on uncertain network results the UI requires a refresh. Async responses are checked against account/list "generation" tokens so stale responses don't overwrite newer state — follow this pattern.
- Never put credentials, signed media URLs, private messages or user media into fixtures.
- Releases: bump versions in `Scripts/build-app.sh` (macOS) / `Apps/iOS/Info.plist` (iOS), update `CHANGELOG.md` and `GuideContent.currentUpdates` in `Sources/BiliGlass/FeatureGuide.swift`, archiving the previous entry in the guide's release history. Change `GuideContent.revision` only when guide content changes (`GuideUpgradeTests` covers this). Keep the About page consistent with `THIRD_PARTY.md`.
- `QA.md`, `CODE_REVIEW.md`, `IOS_STATUS.md` record what was actually verified; don't claim fixes or coverage beyond what was tested.
